# Kapa Oil Superset deployment — customizations reference

Portable record of every change made to this Superset checkout, why, and how to replicate
it on another instance. Move this file wherever you need it — it's self-contained.

Source of truth for the exact diffs: `git diff superset/config.py docker/pythonpath_dev/superset_config.py docker-compose.yml docker/nginx/nginx.conf` on this checkout. Re-pull that diff before copying anything if this doc and the repo ever drift.

## What this deployment does differently from stock Superset

1. Terminates TLS at nginx for a real domain (`kapa-bi-01.kapa-oil.com`) instead of plain HTTP.
2. Embeds dashboards into an external app (`merchandiser.otmretail.ai`, plus a `localhost:4200` dev origin) via guest tokens — CORS, CSP/frame-ancestors, and cross-site cookies all relaxed/configured specifically for that.
3. Runs async chart queries (`GLOBAL_ASYNC_QUERIES`) and scheduled reports (`ALERT_REPORTS`) against Redis, instead of stock's `NullCache`/synchronous defaults.
4. A handful of performance tweaks (HTTP/2, connection pooling, Redis DB layout, worker concurrency).

## 1. `superset/config.py` — do NOT edit this file on a fresh instance

**Important:** this is Superset's own shipped default-config module. On this instance it got edited directly, which is not the recommended pattern — it means every value here is baked into the app source rather than layered on top via override. **On the new instance, don't touch `superset/config.py` at all.** Everything below that lives there should instead go into `docker/pythonpath_dev/superset_config.py` (Section 2), which is the correct override point and loads after `config.py`. This doc lists what changed here only so you know what to reproduce, not where to put it again.

| Setting | Stock default | Kapa value | Purpose |
|---|---|---|---|
| `ENABLE_PROXY_FIX` | `False` | `True` (+ `PROXY_FIX_CONFIG = {"x_for":1,"x_proto":1,"x_host":1,"x_port":1,"x_prefix":1}`) | Trust nginx's `X-Forwarded-*` headers (required behind any reverse proxy) |
| `SESSION_COOKIE_DOMAIN` | unset | `"kapa-bi-01.kapa-oil.com"` | Pin session cookie to your real domain — **set this to the new instance's own domain, not Kapa's** |
| `DASHBOARD_RBAC` (feature flag) | `False` | `True` | Per-dashboard role-based access control |
| `SSH_TUNNEL_LOCAL_BIND_ADDRESS` | `"127.0.0.1"` | `"redis"` | ⚠️ **Looks like a mistake, not a deliberate customization.** This is the local bind address for DB SSH-tunnel connections and has nothing to do with Redis. Recommend leaving this at the stock `"127.0.0.1"` on the new instance unless you know why it was changed here. |
| `CACHE_CONFIG` / `DATA_CACHE_CONFIG` | `NullCache` | Redis-backed (db 1 / db 2 respectively) | See Section 2 — the config actually *in effect* here comes from `docker/pythonpath_dev/superset_config.py`, which overrides these again. Don't bother replicating the version in `config.py`; go straight to Section 2. |
| `RESULTS_BACKEND` | `None` | `RedisCache` on db 3 | Same — superseded by Section 2's version. |
| `SESSION_COOKIE_SECURE` | `False` | `True` | Required once you're on HTTPS |
| `SESSION_COOKIE_SAMESITE` | `"Lax"` | `"None"` | Required for the dashboard to work inside a cross-site iframe |
| `GLOBAL_ASYNC_QUERIES_REDIS_CONFIG.host` | `"127.0.0.1"` | `"redis"` | Points at the docker-compose Redis service name |
| `GLOBAL_ASYNC_QUERIES_JWT_SECRET` | `"test-secret-change-me"` | reads `os.environ.get("GLOBAL_ASYNC_QUERIES_JWT_SECRET")`, falls back to the stock placeholder | **Generate a fresh secret for the new instance** — see Section 6. Must be ≥32 characters or Superset refuses to start once `GLOBAL_ASYNC_QUERIES` is on. |
| `GLOBAL_ASYNC_QUERIES_WEBSOCKET_URL` | `"ws://127.0.0.1:8080/"` | `"ws://superset-websocket:8080/api/v1/ws/"` | Points at the actual `superset-websocket` compose service. The Kapa instance had this wrong (pointed at `redis:8080`) until this was found and fixed — currently harmless since transport is `polling`, but fix it correctly from the start on the new instance. |
| `GUEST_ROLE_NAME` | `"Public"` | `"Gamma"` (custom role, not a stock name) | The FAB role guest-token users are granted. **On the new instance, this must be a role that actually exists** with read access to whatever charts/dashboards/datasets you intend to embed — don't just copy the string "Gamma" onto an instance that doesn't have that role. Either reuse an existing role (e.g. `Alpha`/`Gamma` if present) or create one scoped to what guests should see. |
| `GUEST_TOKEN_JWT_SECRET` | `"test-guest-secret-change-me"` | reads `os.environ.get("GUEST_TOKEN_JWT_SECRET")`, falls back to stock placeholder | **Generate a fresh secret** — see Section 6. |
| `ASYNC_QUERY_JWT_SECRET` | n/a | added, reads env var | Dead/unused config key (confirmed unused by any Superset code path) — kept only for backward-compat with what was already referencing it. Safe to skip entirely on a fresh instance. |

## 2. `docker/pythonpath_dev/superset_config.py` — the correct place for all of the above

This is the file that actually wins at runtime (it's imported on `PYTHONPATH` and loads after `superset/config.py`). **Everything here is what to actually copy onto the new instance's equivalent file.**

## 4. `docker/nginx/nginx.conf`

Full replacement content (adjust `server_name`, cert filenames, and CORS/CSP origins in the paired `superset_config.py` to match your new domain):

```nginx
# ... existing http{} block up to keepalive settings ...
    keepalive_timeout  30;
    # GOTCHA (hit and fixed on the Kapa instance): do NOT leave this low.
    # A value of "2" is harmless under HTTP/1.1 (browsers just open a new
    # connection per request) but breaks HTTP/2 outright — HTTP/2 multiplexes
    # many chart/filter requests over ONE connection, and nginx tears the
    # connection down (killing in-flight streams) once this cap is hit,
    # producing "some charts fail to fetch" on any dashboard with more than
    # a couple of concurrent requests. Use nginx's own default (1000).
    keepalive_requests 1000;
    # ... gzip block unchanged ...

    upstream superset_app { server host.docker.internal:8088; keepalive 100; }
    upstream superset_websocket { server host.docker.internal:8080; }

    # Redirect HTTP to HTTPS
    server {
        listen 80 default_server;
        server_name YOUR-DOMAIN-HERE;
        location / { return 301 https://$host$request_uri; }
    }

    # Internal HTTPS access via port 443
    server {
        listen 443 ssl;
        http2 on;
        server_name YOUR-DOMAIN-HERE;

        ssl_certificate /etc/nginx/certs/YOUR-CERT.crt;
        ssl_certificate_key /etc/nginx/certs/YOUR-KEY.key;
        ssl_protocols TLSv1.2 TLSv1.3;
        ssl_prefer_server_ciphers on;
        ssl_ciphers HIGH:!aNULL:!MD5;

        location /ws {
            proxy_pass http://superset_websocket;
            proxy_http_version 1.1;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection "Upgrade";
            proxy_set_header Host $host;
        }

        location / {
            proxy_pass http://superset_app;
            proxy_set_header Host $host:$server_port;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Host $host:$server_port;
            proxy_set_header X-Forwarded-Proto https;
            proxy_set_header X-Forwarded-Port $server_port;
            proxy_http_version 1.1;
            port_in_redirect off;
            proxy_connect_timeout 300;
        }
    }

    # External access via port 8443 (drop this block if you don't need a
    # second, differently-firewalled entry point)
    server {
        listen 8443 ssl;
        http2 on;
        server_name YOUR-DOMAIN-HERE;
        # ... identical to the 443 block above ...
    }
}
```

## 5. Secrets and certs hygiene — apply this from day one on the new instance

Lessons learned the hard way on the Kapa instance (real secrets were briefly hardcoded directly into tracked `.py` files and real TLS keys sat ungitignored in the working tree — caught and fixed before anything was committed, but avoid repeating it):

1. **Never hardcode secret literals in `superset/config.py` or `superset_config.py`.** Always `os.environ.get("SOME_VAR") or "<safe-non-secret-fallback>"`.
2. **Real secret values go in `docker/.env-local`** (already gitignored via the root `.gitignore` rule `docker/*local*`, and already wired into every relevant service's `env_file:` in stock `docker-compose.yml`):
   ```
   GLOBAL_ASYNC_QUERIES_JWT_SECRET=<generate fresh, ≥32 chars>
   GUEST_TOKEN_JWT_SECRET=<generate fresh>
   SUPERSET_WEBSOCKET_JWT_SECRET=<generate fresh, ≥32 chars>
   ```
   Generate with e.g. `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`. **Do not reuse the Kapa instance's actual secret values on a different instance.**
3. **`docker/nginx/certs/` needs its own `.gitignore`** the moment you put real cert/key material there:
   ```
   # docker/nginx/certs/.gitignore
   *
   !.gitignore
   ```
4. After creating/editing `docker/.env-local`, remember: `docker compose restart` does **not** reload `env_file:` — you need `docker compose up -d --force-recreate <service>` or the container keeps running with stale/missing env vars. (This caused a full crash-loop on the Kapa instance the first time — `GLOBAL_ASYNC_QUERIES_JWT_SECRET` fell back to the 22-character stock placeholder, which is under Superset's hard 32-byte minimum once `GLOBAL_ASYNC_QUERIES` is on, and the app refused to start.)
5. Also editing `docker/nginx/nginx.conf` (or any bind-mounted file) sometimes isn't picked up by `nginx -s reload` depending on the Docker file-sharing backend — if a reload doesn't seem to take effect, `docker compose up -d --force-recreate nginx` instead.

## 6. Gunicorn proposal — for implementation on the test instance (not yet applied here)

**Current state (both here and stock Superset's `docker-compose.yml`):** the `superset` service runs
`docker/docker-bootstrap.sh app`, which unconditionally launches:
```
flask run -p 8088 --with-threads --reload --debugger --host=0.0.0.0
```
— the Werkzeug **development** server, regardless of `DEV_MODE`/`SUPERSET_ENV` settings (those aren't consulted by this code path at all). `--reload` adds filesystem-watching overhead and `--debugger` adds the Werkzeug debugger; more importantly, it's fundamentally single-process and doesn't parallelize the way a dashboard's burst of concurrent chart/filter requests needs.

A `app-gunicorn` branch already exists in the same script and runs `/usr/bin/run-server.sh` (gunicorn, `gthread` worker class) instead — nothing currently invokes it.

### Why this matters
Every chart and every native filter on a dashboard fires its own request in parallel on page load (confirmed in the frontend source — this is standard Superset behavior, not something either instance customized). A single dev-server process has to handle that whole burst serially/thread-bound; gunicorn with multiple worker processes handles it as true parallel capacity. This is the single biggest lever for concurrent dashboard load performance of everything covered in this doc.

### Proposed change (test instance only, until proven out)
1. In `docker-compose.yml`, change the `superset` service's command:
   ```yaml
   command: ["/app/docker/docker-bootstrap.sh", "app-gunicorn"]
   ```
2. `run-server.sh` is driven by env vars — none of these are currently set anywhere in `docker/.env`/`docker/.env-local`, so it would run with gunicorn's bare defaults (`--workers 1 --threads 20 --timeout 60`). Set explicit values instead, added to `docker/.env-local`:
   ```
   SERVER_WORKER_AMOUNT=4        # start at (2 x CPU cores) + 1, tune from there
   SERVER_THREADS_AMOUNT=20
   GUNICORN_TIMEOUT=60
   GUNICORN_KEEPALIVE=2
   ```
3. Because each gunicorn worker opens its **own** SQLAlchemy connection pool against Postgres, revisit the `SQLALCHEMY_ENGINE_OPTIONS` pool sizing from Section 2 once you know the worker count: total possible connections ≈ `SERVER_WORKER_AMOUNT × (pool_size + max_overflow)`. With 4 workers × (10+20) = up to 120 connections — check this against Postgres's `max_connections` (`SHOW max_connections;`) before going live, and lower `pool_size`/`max_overflow` if needed.
4. You lose `--reload` (auto code-reload on file change) — fine for a deployed instance, but if this test instance doubles as an active dev environment, keep a way to flip back to `docker-bootstrap.sh app` for active development sessions.
5. **Load test before trusting it**: hit the instance with a realistic burst (a dashboard with the same rough chart/filter count you expect in production) both before and after the switch, and watch for connection pool exhaustion or worker OOM under load — tune `SERVER_WORKER_AMOUNT`/`SERVER_THREADS_AMOUNT` from there rather than guessing once.

### Verification checklist for the test instance
- `docker compose logs superset` should show gunicorn's startup banner (worker count, `gthread` class), not "Starting web app (using development server)...".
- `docker compose exec superset ps aux` should show multiple `gunicorn` worker processes, not a single `flask` process.
- Concurrent chart-burst test (open a real dashboard, watch the Network tab) shouldn't show requests queuing/timing out the way they might under the dev server.
- `docker compose exec db psql -U superset -d superset -c "SELECT count(*) FROM pg_stat_activity WHERE datname='superset';"` under load — confirm it stays under Postgres's `max_connections`.

## 7. Post-replication verification (general)

- `docker compose exec superset python -c "from flask import current_app; print(len(current_app.config['GLOBAL_ASYNC_QUERIES_JWT_SECRET']))"` → should print your fresh secret's length (≥32), not 22 (which means the fallback placeholder is being used, i.e. `docker/.env-local` isn't loading).
- `docker compose exec nginx nginx -t` after any nginx.conf change.
- `curl -vk --http2 https://YOUR-DOMAIN/ ` → confirm `HTTP/2` is negotiated.
- Issue a real guest token and load an embedded dashboard end-to-end — confirm no 401 "Not authorized" on chart/filter requests (the async-token cookie SameSite/Secure gotcha from Section 2) and no partial-load failures (the nginx keepalive_requests gotcha from Section 4).
- `git status` / `git check-ignore -v docker/nginx/certs/*` → confirm no real secrets or cert/key files are sitting un-ignored before your first commit on the new instance.
